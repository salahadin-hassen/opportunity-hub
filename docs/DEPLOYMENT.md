# Deploying Opportunity Hub

This guide puts Opportunity Hub on the public internet at **no cost**. It uses Render for the frontend and API
and Neon for a persistent PostgreSQL database. Everything that doesn't need an account is already in the
repository: `render.yaml`, production settings, a production-safe seed and a smoke test. The steps below are
the parts that need you: creating accounts and pasting one secret.

---

## 1. Architecture

```
 Browser ──HTTPS──▶  Render static site      opportunity-hub.onrender.com      (frontend, CDN, never sleeps)
    │
    └────HTTPS──▶  Render web service       opportunity-hub-api.onrender.com  (FastAPI, Frankfurt)
                         │  TLS
                         ▼
                   Neon PostgreSQL 16        eu-central-1 (Frankfurt)          (persistent database)
```

- **The frontend calls the API cross-origin.** `VITE_API_BASE` is fixed at build time, and the API allows
  exactly that one origin through `CORS_ORIGINS`. There's no wildcard, and no cookies are used: tokens travel
  in the `Authorization` header.
- **Migrations run before the API starts.** The start command is `alembic upgrade head && uvicorn …`, so the
  service only becomes healthy on the current schema. `/health` returns 200 only when the database answers.
- **Frankfurt** is the closest Render region to an East African audience. Choose Neon's Frankfurt region too,
  to keep the API and the database close.

### Why this combination

| Need | Choice | Why |
| --- | --- | --- |
| Frontend | Render static site, free | Served from a CDN, never sleeps, SPA rewrite built in |
| API | Render web service, free | Runs FastAPI natively; health checks; deploys from GitHub |
| Database | **Neon, free** | Permanent free plan with 1 GB and no card. Render's free Postgres **expires after 30 days** and is deleted 14 days later, with no backups. |

### Costs and limits (checked against the providers' pages on 31 Oct 2026; re-check before relying on them)

| Item | Cost | Limit that matters for the demo |
| --- | --- | --- |
| Render static site | $0 | Counts against the workspace's included bandwidth and build minutes |
| Render free web service | $0 | **Sleeps after 15 minutes without traffic. The first request takes about one minute** to wake it. 750 instance hours a month. The filesystem isn't persistent (nothing relies on it). |
| Neon free | $0, no card | 1 GB per project, 100 compute hours a month. Compute suspends after 5 minutes idle (wake-up is near-instant). |

**To remove the cold start:** Render's paid web-service plan (Starter) keeps the API awake. Check the current
price on render.com/pricing before choosing it. Nothing here needs a paid plan. Railway is a workable
alternative, but it has no permanent free plan (trial credit, then a monthly fee). Don't start either without
deciding on the cost.

## 2. One-time setup

### 2.1 Push the release branch
Render deploys from GitHub. The release commit is on `feat/opportunity-hub-product`
(see the release report for whether it's already pushed).

### 2.2 Create the database (Neon)
1. Sign up at https://neon.com (free, no card).
2. Create a project: **Postgres 16**, region **AWS Europe (Frankfurt) eu-central-1**.
   Postgres 16 matches local development and the `pg_dump` used for backups.
3. Copy the **direct** connection string (not the "pooled" one). It looks like
   `postgresql://<user>:<password>@ep-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=require`.
   Treat it as a password.

### 2.3 Create the services (Render Blueprint)
1. Sign up at https://render.com and connect GitHub (grant access to `salahadin-hassen/opportunity-hub`).
2. **New → Blueprint**, then choose the repository and branch `feat/opportunity-hub-product`. Render reads
   `render.yaml`.
3. When asked for `DATABASE_URL`, paste the Neon connection string. `JWT_SECRET` is generated by Render;
   leave it alone.
4. Apply. Render builds both services. The API runs the migrations, then starts.

### 2.4 If the service names were taken
Render URLs are global. If `opportunity-hub` or `opportunity-hub-api` was taken, Render adds a suffix. Then:
- API service → Environment → set `CORS_ORIGINS` to the **frontend's** real URL, for example
  `https://opportunity-hub-ab12.onrender.com`.
- Static site → Environment → set `VITE_API_BASE` to the **API's** real URL, then **Manual Deploy → Clear
  build cache & deploy**. The value is baked in at build time.

### 2.5 Seed the demo data once
Render's free plan has no shell, so run the production seed from your machine against Neon. This is a
one-off script, not the server:

```bash
cd backend
APP_ENV=production \
JWT_SECRET="$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')" \
DATABASE_URL='<the Neon connection string>' \
DEMO_PASSWORD="$(cat ../.release/production-demo-password.txt)" \
.venv/bin/python -m scripts.seed_demo --allow-production
```

- `JWT_SECRET` only lets the settings load here. The script never signs tokens.
- **Production mode never deletes anything users created.** It inserts missing opportunities and skills,
  then resets the demo account. Running it again is safe: "0 created".
- The demo password lives in the git-ignored `.release/production-demo-password.txt` (owner-only). It is
  never in the repository or the frontend.

## 3. Verify the deployment

Replace the URLs with yours.

```bash
API=https://opportunity-hub-api.onrender.com
WEB=https://opportunity-hub.onrender.com

curl -s $API/health                       # {"status":"ok"} (the first call may take ~1 minute: cold start)
curl -s "$API/opportunities?limit=100" | python3 -c "import json,sys; print(len(json.load(sys.stdin)))"   # 12
curl -si -X OPTIONS $API/auth/login -H "Origin: $WEB" \
  -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type" | grep -i allow-origin
curl -s -o /dev/null -w "%{http_code}\n" $WEB/discover   # 200 (SPA fallback for direct links)

# The browser smoke test: creates no accounts, uses only the demo account.
cd frontend
OH_BASE_URL=$WEB OH_API_URL=$API DEMO_PASSWORD="$(cat ../.release/production-demo-password.txt)" \
  npx playwright test e2e/smoke.spec.ts
```

After the smoke test, reset the demo account (step 2.5 with `--demo-user-only`). Then check by hand on a
phone and a laptop, in both themes: register a throwaway account, complete onboarding, run a check, open a
detail page, and confirm direct links and refreshes work.

## 4. Configuration reference

### Backend (Render environment)

| Variable | Production value | Notes |
| --- | --- | --- |
| `APP_ENV` | `production` | Enables the strong-secret check and the seed guard |
| `DATABASE_URL` | Neon connection string | `postgres://` is accepted and normalized |
| `JWT_SECRET` | generated by Render | Startup fails if it's shorter than 32 characters or the example value |
| `CORS_ORIGINS` | the frontend URL | Comma-separated explicit origins; `*` is rejected |
| `AUTH_RATE_LIMIT_PER_MINUTE` | `10` | Login and registration attempts per client IP per minute (HTTP 429 beyond) |
| `ALLOWED_HOSTS` | *(unset)* | Optional Host-header allow-list. Left unset on Render because its health checker's Host header isn't documented. |
| `ADMIN_API_TOKEN` | *(unset)* | Unset disables `POST /opportunities` entirely (HTTP 403) |
| `PYTHON_VERSION` | `3.12.7` | |

### Frontend (Render static site, build time)

| Variable | Value |
| --- | --- |
| `VITE_API_BASE` | the API URL. Unset means same-origin `/api` (local development or behind a proxy). |
| `NODE_VERSION` | `22` (Vite 7 needs Node 20.19+) |

`.env` files are never committed. The templates are `backend/.env.example` and
`frontend/.env.production.example`.

## 5. Operations

**Database backups.** Neon's free plan includes limited point-in-time history; check the console for the
current window. For a dependable copy, export before the demo and after anything important:

```bash
pg_dump --no-owner --no-privileges '<Neon connection string>' > opportunity-hub-$(date +%F).sql
```

Restore into an empty database with `psql '<connection string>' < file.sql`.

**Redeploys** keep all data: the database is external and migrations only move forward. A redeploy re-runs
`alembic upgrade head`, which does nothing when the schema is current.

**Don't** run the development seed (without `--allow-production`) against production. It refuses in production
mode. Don't point any production setting at the local `.devdb` cluster.

**Before a presentation**, open `$API/health` and the frontend 2–3 minutes before you start, so the free API is
awake. Use the presenter checklist in `docs/DEMO_RUNBOOK.md`.
